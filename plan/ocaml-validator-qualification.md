# OCaml Validator & Fallback Toolchain Qualification Strategy (`cert-validator` / `verified-opt-fallback`)

**Applicable Standards:** `ISO 26262-8 §11` (`TD1` / `TCL1` verification checker), `IEC 61508 T2/T3`, `DO-330 TQL-5`  
**Toolchain Baseline:** Pinned OCaml `4.14.x` switch, Dune `3.14`, Menhir `3.0`, Zarith (`vellvm/rocq-vellvm.opam`)  
**Scope:** Extracted Rocq checker `cert-validator` & verified fallback `verified-opt-fallback` with `<= 750` LOC handwritten OCaml glue (`verify_repo_integrity.py`)

---

## 1. Fail-Safe Tool Role & Binary Distribution Model

- `cert-validator` generates **no** target machine code and performs **no** IR transformations. It emits a strictly binary accept (`exit 0`) vs. reject (`exit 2/3/4`) verdict over `(src.ll, tgt.ll, fn.cert)` or `--check-merge` inputs.
- Under `ISO 26262-8 §11`, a latent bug in `ocamlopt` could violate soundness **only** if it miscompiled extracted Rocq checker logic such that an invalid certificate silently returned `exit 0` instead of non-zero; crashes or false rejections remain fail-safe (routing the function to `verified-opt-fallback` or aborting compilation).
- End-users consume **pinned, prebuilt Release binaries** packaged directly from reproducible CI builds (`llvm-cert-rocq-tools-linux-x86_64.tar.zst` with `SHA256SUMS.txt` and `TOOLCHAIN.txt`), rather than compiling OCaml sources on customer build hosts.

---

## 2. Four-Pillar Qualification Evidence

### Pillar 1 — Strict Toolchain & Build Pinning
- Exact OCaml switch (`4.14.x`), `rocq`, `dune`, and opam dependency versions are pinned via [`vellvm/rocq-vellvm.opam`](../vellvm/rocq-vellvm.opam) and recorded verbatim in `TOOLCHAIN.txt` on every CI artifact export.
- Handwritten OCaml outside Rocq `ml/extracted/` is hard-capped by [`scripts/verify_repo_integrity.py`](../scripts/verify_repo_integrity.py) (`MAX_HANDWRITTEN_OCAML_LOC = 750`, currently `700/750`), with 64 MiB input size limits and top-level exception guards preventing uncaught `Stack_overflow` or `Out_of_memory` crashes (`cert_validator.ml`).

### Pillar 2 — Dual-Compiler Differential Execution (`ocamlopt` Native vs. `ocamlc` Bytecode)
- [`vellvm/src/ml/bin/dune`](../vellvm/src/ml/bin/dune) builds **both** binaries in `(modes native byte_complete)`:
  - `cert-validator` / `verified-opt-fallback` compiled by **`ocamlopt`** (native x86_64 Flambda/code generator; `-Oclassic` on `libvellvm` + `-O3` on `extracted`), and
  - `cert-validator.bc` / `verified-opt-fallback.bc` compiled by **`ocamlc`** (independent stack-based bytecode compiler and C runtime interpreter, using an entirely separate code generator).
- Every CI run executes the full positive, forged-certificate, and mutation test suites on **both** executables and asserts **100% exit-code equality** (`native.returncode == bytecode.returncode`), plus **byte-for-byte identical IR output** across `verified-opt-fallback` and `verified-opt-fallback.bc`.

### Pillar 3 — Deterministic Certificate & IR Mutation Campaign + Branch Coverage
- [`scripts/run_cert_mutation_suite.py`](../scripts/run_cert_mutation_suite.py) executes two complementary suites on both native and bytecode builds:
  1. The 28-case Layer-2 corpus ([`run_forged_cert_suite.py`](../scripts/run_forged_cert_suite.py)).
  2. A deterministic **200+ case mutation campaign** applying structured semantic corruptions (forged `nsw`/`nuw`/`fast`/`noreturn`/`noundef` flags, altered bit widths, SHA-256 bit flips, reversed poison folds, corrupted registers, stripped/truncated S-expressions) plus deterministic byte/bit-level mutations across valid `.cert` and `.ll` pairs.
- **Mandatory Gate:** `100%` mutation detection (`0` escaped mutations), `0` crashes (`Stack_overflow`, `Fatal error: exception`, `Assert_failure`), `0` timeouts, and `100%` native/bytecode parity.
- **Planned Extension (Phase 6.3b):** Separate dev/coverage profile using `bisect_ppx` to measure and audit branch coverage over `cert-validator` across the forged, mutation, and cross-repo E2E test suites without modifying release binaries.

### Pillar 4 — Restricted Language Subset & Pre-Release Bug-Tracker Screening
1. **Restricted OCaml Subset Audit:** Confirm prior to every release that extracted code (`ml/extracted/`) plus thin CLI/parser glue (`ml/bin/`, `ml/libvellvm/`, `ml/IO.ml`) uses purely sequential functional execution, zero custom C-FFI bindings beyond `zarith`/stdlib, zero multicore/threads, and contains `Obj.magic` *only* where generated by Rocq's standard extraction pass.
2. **Release Artifact Manifest Check:** Verify `TOOLCHAIN.txt` tool versions and `SHA256SUMS.txt` digests match CI logs (`rocq-ci.yml`).
3. **Upstream Bug-Tracker Screening:** Before cutting any customer release tarball, screen the OCaml `4.14.x` / `x86_64-linux` / `Flambda` issue tracker for any `ocamlopt`, `ocamllex`, `menhir`, or `zarith` code-generation errata discovered since the previous release and document the disposition in the release TQK notes.
